Since your legacy application uses Python for the backend and React + TypeScript + Next.js for the frontend, the best approach is to give your coding agent a precise implementation prompt that integrates the Finance workflow into your existing codebase.

## 6. Component 05 — Reconciliation and closure

This component should calculate the financial outcome rather than let users manually type a balance.

For a straightforward cash advance:

\\[ \text{Outstanding Advance} = \text{Funds Released} - \text{Approved Expenses} - \text{Funds Returned} \\]

For example, if PHP 10,000 was released, PHP 8,700 of expenses was approved, and PHP 1,300 was returned, the remaining advance balance is zero.

The system should separately track:

- Released amount.
- Total claimed expenses.
- Approved expenses.
- Rejected and pending expenses.
- Unused funds expected to be returned.
- Actual returned funds and their payment evidence.
- Additional reimbursement due, if any.
- Remaining advance balance.
- Accounting posting or reconciliation reference.
- Closure reviewer, closure timestamp, and closure reason where applicable.

Do not close a record merely because the calculated balance is zero if required evidence, approval, or accounting reconciliation is still outstanding. Conversely, do not treat an unapproved expense as a settled expense.

## 5. Regression verification — the actual tests you need

Stage 5 should not be considered complete just because the dashboard renders. It must demonstrate that earlier stages still work and that the displayed figures agree with the underlying records.

## Regression test groups

1\. Database integrity tests

Verify foreign keys, unique identifiers, valid state transitions, monetary precision, and correct relationships between advances, expense lines, payables, payments, and reconciliation records.

2\. RBAC and authorization tests

Verify employee, approver, Finance, and administrator permissions. Confirm users cannot retrieve unauthorized employee records, approve prohibited transactions, or alter audit history.

3\. End-to-end workflow tests

Test request → approval → release → liquidation → reconciliation → closure, plus the separate purchase request → payable validation → payment tracking → reconciliation flow.

4\. Dashboard accuracy tests

Seed known test records, query the dashboard, and compare its totals, ratios, date filters, pagination, and status counts with independently verified expected results.

5\. Audit and evidence tests

Confirm sensitive state changes produce attributable events and that failed actions, missing evidence, and reconciliation exceptions are handled correctly.

6\. Frontend and release checks

Run component and browser tests, type checking, linting, production builds, migration checks, and the existing regression suite. Report any failures instead of assuming success.

These verification practices align with OWASP's guidance on testing authorization and logging, and on preserving enough event detail to reconstruct sensitive operations.&#x20;

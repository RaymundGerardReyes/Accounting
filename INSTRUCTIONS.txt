The prompt should require the agent to inspect your actual infrastructure first, preserve existing functionality, and implement the cash advance, expense liquidation, Purchase Request, approval, bank transaction tracking, and reconciliation components as one coherent system.

It should also distinguish the application's operational records from actual accounting records: a successful form submission is not proof of payment, and an approved liquidation is not automatically proof that every outstanding balance has been settled.

## Copy-ready implementation prompt

Use the following prompt in your coding agent with your legacy repository open. It is designed to require repository inspection, incremental implementation, and evidence-based testing rather than generating a disconnected demo.

# IMPLEMENTATION SPECIFICATION: Finance Operations, Cash Advances, Expense Liquidation & Purchase-to-Pay

## 1. Role and objective

Act as a Senior Software Engineer, Solutions Architect, and Finance Systems Analyst implementing an auditable Finance Operations module inside my EXISTING LEGACY CODEBASE.

The application stack is:

- Backend: Python. Identify the actual framework from the repository before making changes.
- Frontend: React, TypeScript, and Next.js.
- Database, authentication, RBAC, file storage, and deployment: inspect the existing implementation; do not assume technologies that have not been verified.

Your objective is to integrate the business workflows below into the existing application while preserving working functionality, architecture, conventions, APIs, database structures, and integrations wherever possible.

This is a production-oriented implementation, not a mockup, static dashboard, disconnected demo, or UI-only prototype.

## 2. Mandatory repository inspection

Before modifying code:

1. Inspect the repository structure, README, dependency manifests, environment configuration, database models, migrations, existing API routes, service layers, frontend pages, shared components, authentication, RBAC, file storage, and test suites.
2. Identify existing finance-related features, reusable components, status enums, audit logs, and integration points.
3. Produce a concise implementation map containing:
   - Existing reusable components.
   - Existing components requiring modification.
   - Missing capabilities.
   - Relevant files and dependencies.
   - Database migration requirements.
   - Security and backward-compatibility risks.
4. Compare the existing implementation against the requirements below. Classify each requirement as Implemented, Partially Implemented, Missing, or Requires Business Confirmation.
5. Do not recreate a capability that already exists and meets the requirements.
6. Do not replace the backend framework, database, authentication system, UI component library, or deployment infrastructure without a demonstrated technical necessity and explicit approval.
7. If a material business rule is ambiguous, document the ambiguity and implement only the safe, configurable portions. Do not silently invent company policy.

After the inspection, proceed incrementally through implementation, testing, and verification. Do not stop at a proposed plan when the repository and available environment permit implementation.

## 3. Business workflows to implement

### A. Cash Advance Request

Implement the complete request lifecycle.

Required information:

- Unique advance identifier.
- Requestor and employee ID.
- Department and cost center, where applicable.
- Business purpose and justification.
- Requested amount and currency.
- Date needed.
- Activity or travel dates, where applicable.
- Remarks.
- Supporting attachments.
- Submission timestamp.
- Approval history and liquidation deadline.

Required actions:

- Save draft.
- Submit request.
- Approve or reject with an attributable decision and reason.
- Return for correction, if supported by the approved policy.
- View request history and supporting documents.

Prevent duplicate submissions and unauthorized status changes.

Approval must not imply that the funds have been released.

### B. Expense Report and Cash Advance Liquidation

Implement transaction-level expense recording.

Each expense line should support:

- Transaction date.
- Merchant or payee, when available.
- Amount and currency.
- Expense category.
- Business purpose.
- School, activity, or destination where applicable.
- Receipt or invoice attachment.
- Out-of-base documentation, including MFAR where required.
- Validation and review status.
- Return for correction or line-level adjustment.

Each report should support:

- Related cash advance, if liquidating an advance.
- Direct reimbursement request, if no advance was issued.
- Summary of total expenses, advance received, net due to company, or net due to employee.
- Required review and approval workflow.
- Settlement status tracking: whether excess funds were returned to the company or reimbursable amounts were paid to the employee.

An approved expense report does not close the liquidation until the net financial balance is confirmed settled.

### C. Purchase Request, Quotations, and Purchase Order

Implement the procurement workflow.

Required components:

- Purchase Request (PR) with line items, estimated costs, and budget confirmation.
- Minimum 3 vendor quotations for requests exceeding the configured threshold.
- Quotation comparison and selection justification.
- Purchase Order (PO) generation upon PR approval.
- Matching of PO to vendor invoice and receiving report before payment authorization.

Track the status of each document independently: Draft, Submitted, Approved, Rejected, Ordered, Received, Invoiced, Paid.

### D. Bank Transaction Import, Staging, and Rule-Based Matching

Implement a bank transaction staging pipeline:

- CSV and statement import with format validation.
- Duplicate detection by transaction date, reference number, amount, and account.
- Status tracking: Staged, Auto-Matched, Manually Matched, Categorized, Posted, and Excluded.
- Rule-based auto-matching engine:
  - Match by exact reference or invoice number.
  - Match by payee name and exact amount within a date window.
  - Match by recurring transaction pattern.
- Manual matching interface for transactions that cannot be matched automatically.
- Audit trail for all match, unmatch, and categorization actions.

Imported transactions must remain in the staging area until validated. Do not write directly to the primary financial ledger during import.

### E. Account Reconciliation

Implement monthly account reconciliation:

- Bank account and reporting period selection.
- Statement opening and closing balance entry.
- Automatic calculation of reconciled balance from matched transactions.
- Discrepancy detection between statement balance and book balance.
- Support for outstanding checks, deposits in transit, and bank adjustments.
- Reconciliation sign-off workflow: Preparer submission, Reviewer verification, and Approver sign-off.
- Lock reconciled periods to prevent retrospective modification.

### F. Separation of Duties and Approval Hierarchy

Enforce role-based financial authority:

- Requester cannot approve their own advance, expense report, PR, or exception.
- Tiered monetary approval limits:
  - Tier 1: Department Manager up to configured limit.
  - Tier 2: Finance Controller above Tier 1 limit.
  - Tier 3: Managing Director / Executive for high-value transactions.
- Dual authorization for bank disbursements and payment releases.
- Preparer of a bank reconciliation cannot be the sole approver.
- Capture timestamp, IP address, user ID, decision, and comments on every approval action.

### G. Audit Trail and Reporting

Record immutable audit logs for:

- All state transitions across advances, liquidations, PRs, POs, bank transactions, and reconciliations.
- Document uploads, replacements, and status changes.
- Policy exception requests and decisions.
- Manual match, unmatch, and categorization overrides.

Provide operational reports:

- Aging of outstanding cash advances.
- Unliquidated advances by department and employee.
- Budget vs. actual spending by department and cost center.
- Bank reconciliation discrepancy report.
- Vendor spending summary.

## 4. Policy Configuration & Exception Handling

Serve these as the initial approved configuration only; do not embed them as permanent business-rule constants in application code.

## 1. Policy Management

Implement an authorized policy administration module supporting:
- Policy name, description, and scope.
- Applicable employee groups and departments.
- Monetary limits and currency.
- Reporting-frequency limits and reporting-period definitions.
- Submission deadlines.
- Required document rules.
- Exception eligibility and required approval authority.
- Effective-from and effective-until dates.
- Draft, Pending Approval, Active, and Retired policy states.
- Version history and change justification.

Require appropriate authorization and approval before a policy becomes active. Prevent unauthorized users from modifying policy configuration.

## 2. Policy Evaluation

Implement a reusable backend policy evaluation service.

Evaluate the applicable policy version against:
- Authenticated employee identity and eligibility.
- Reporting period.
- Existing submissions and relevant report states.
- Claimed monetary amount.
- Required evidence and document completeness.
- Applicable frequency and other configured rules.
- Existing exception decisions.

Return structured validation results, including rule identifier, severity, outcome, explanatory message, and whether an exception is permitted.

The frontend must display validation results from the backend. It must not independently decide whether a financial transaction is authorized.

## 3. Exception Management

Implement a separate exception request and approval workflow.

Capture:
- Exception ID.
- Related report and employee.
- Applicable policy version and violated rule.
- Requested exception type and amount.
- Business justification.
- Supporting documents.
- Requester and submission timestamp.
- Assigned reviewer.
- Decision, decision reason, approver, and timestamp.
- Scope and expiry of the authorization.

Support Draft, Submitted, Under Review, Approved, Rejected, and Expired states as appropriate.

Enforce independent authorization where required. A requester must not approve their own exception when prohibited by the applicable policy.

An exception must apply only to its authorized transaction, employee, reporting period, amount, and scope. Never turn an individual exception into a global policy change.

## 4. Submission and Transaction Safety

Allow compliant reports to proceed through the normal workflow.

When a policy violation occurs:
- Block or hold the operation according to the rule's configured enforcement mode.
- Permit an exception request only if that rule explicitly allows one.
- Do not treat an exception request as an approval.
- Re-evaluate the transaction when an authorized decision is made.
- Preserve the original submission and all decision history.

Enforce reporting-frequency checks and other financial invariants atomically. Prevent concurrent submissions, retries, or duplicate requests from bypassing controls.

Do not rely on frontend validation, hidden fields, or client-provided employee IDs, roles, limits, or approval states.

## 5. Policy Versioning and Audit

Every evaluated transaction must retain its applicable policy version and evaluation outcome.

Record:
- Policy changes and version numbers.
- Previous and new configuration values.
- Change justification and approving authority.
- Effective dates.
- Exception requests and decisions.
- Validation outcomes and resulting workflow transitions.

Do not silently alter historical decisions when policy configuration changes.

## 6. Testing

Implement tests for:
- Reports within and above the configured monetary limit.
- First and subsequent monthly submissions.
- Draft, cancelled, returned, and submitted report handling.
- Policy changes with different effective dates.
- Prohibited and permitted exceptions.
- Unauthorized and self-approved exceptions.
- Expired exception approvals.
- Concurrent submissions and duplicate retries.
- RBAC and audit history.
- Regression of the existing Cash Advance and Expense Liquidation workflows.

Deliver the database changes, backend services, API endpoints, frontend administration and exception screens, automated tests, and a report of actual test results.

Do not hardcode configurable business-policy values into the frontend or backend. Keep essential security invariants and authorization enforcement in code, while making approved business parameters configurable through controlled administration.

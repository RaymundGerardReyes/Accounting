# Automated Contract & Parity Verification Harness Proposal

**Author**: Senior Release Engineer & Migration Auditor  
**Scope**: Behavioral Parity Verification between Python FastAPI (`Backend/`) and C# ASP.NET Core (.NET 10, `Backend.DotNet/`)

---

## 1. Objective & Scope

The Parity Harness verifies that given identical HTTP requests and identical initial database states, both the Python backend and the .NET 10 backend produce **mathematically equivalent behavior**:
1. **HTTP Status Code** equivalence (e.g. 200, 201, 400, 403, 404, 422).
2. **Response Body Schema & Values** equivalence, utilizing a deterministic JSON normalizer that filters declared volatile fields (`id`, `created_at`, `timestamp`, `correlation_id`, `token`).
3. **HTTP Header Equivalence** on security headers (`Content-Type: application/problem+json`, `X-Content-Type-Options: nosniff`).
4. **Database Side Effects Equivalence**: Identical rows inserted into business tables and identical cryptographic hash-chained audit events written to `audit_events` via `fn_append_audit_event`.

## 2. Architecture & Execution Topology

```
             +---------------------------------------------+
             |         Test Request Matrix (JSON)          |
             +---------------------------------------------+
                                    |
                    +---------------+---------------+
                    |                               |
                    v                               v
         [Python FastAPI :8000]          [.NET 10 Host :5000]
                    |                               |
                    v                               v
         [PostgreSQL DB Snapshot A]      [PostgreSQL DB Snapshot B]
                    \                               /
                     \                             /
                      v                           v
              +-------------------------------------------+
              |       Contract Comparator & Diff Engine   |
              +-------------------------------------------+
                                    |
                    +---------------+---------------+
                    |                               |
                    v                               v
     [Pass: docs/migration/evidence/...]     [Fail: Diff Report]
```

### Safety & Isolation Rules:
- **Disposable Databases Only**: Both runtimes connect to ephemeral local PostgreSQL test containers or isolated test schemas (`accounting_test_py`, `accounting_test_dn`).
- **Never Touch Production or Remote Databases**: Live Supabase, Neon, or production connections are strictly blocked by environment checks.
- **Zero Real Customer Data**: All test fixtures use synthetic, deterministic test data generated by `DeterministicRandom` and `FakeIdGenerator`.

## 3. Comparison Strategy & Volatile Field Masking

### A. Declared Volatile Fields (Ignored in JSON Diff)
- Identifiers: `id`, `*_id`, `order_id`, `payment_id`, `user_id` (when UUIDs are generated nondeterministically).
- Timestamps: `created_at`, `updated_at`, `timestamp`, `expires_at`, `build_time`.
- Correlation: `correlation_id`, `request_id`, `trace_id`.
- Ephemeral tokens: `csrf_token`, `session_token` (entropy verified separately).

### B. Invariant Checks (Strictly Compared)
- Numeric currency amounts: Centavo-exact integer match (e.g. `10000` centavos).
- Financial calculations: VAT amount, gross amount, net amount, advance balance.
- Error codes and reasons: RFC 9457 `type`, `title`, and `error_code` must match.
- State machine statuses: Aggregate states (e.g. `requires_action`, `succeeded`, `posted`, `submitted`).
- Database mutation diff: Count and schema of inserted rows in target tables.

---

## 4. Evidence Artifact Storage

When a route passes the automated parity comparison, an evidence artifact is stored under:
```
docs/migration/evidence/<ROUTE-ID>/
  ├── request.json          # Input payload, query params, headers
  ├── python-response.json  # Raw Python response
  ├── dotnet-response.json  # Raw .NET response
  ├── normalized-diff.json  # Canonical comparison result (0 diffs)
  └── db-side-effects.json   # Audit records & inserted row fingerprints
```
Only when these artifacts are generated and checked into source control does the route transition from `tested` $\rightarrow$ `parity-verified` in `route-ledger.csv`.

---

## 5. Non-Verifiable Edge Cases (Declared Accepted Differences)
The following behaviors cannot be verified via automated local dual-run and require special handling:
1. **Live PayMongo Payment Provider**: Real credit card / GCash checkout webhooks cannot hit live third-party gateways; simulated with `WebhookSigner` and recorded webhook fixtures.
2. **External Google Forms HTTP Callbacks**: Simulated using synthetic Google Form webhook ingestion payloads.
3. **Live SMTP Handshakes**: Dispatched to an in-memory test sink (`FakeEmailSender`) rather than live Gmail SMTP.
